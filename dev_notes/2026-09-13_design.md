# Design, and what was decided against

`dev_notes/2026-09-13_design.md`

The tool converts; it does not decide anything about xlsx, row limits
or recipes. Kris's cut (2026-09-13): "the tool that creates Parquet
from any csv files in the zip should just do that. Normally only one
file will come out, and it will be pretty small. That can then be
converted individually by a much simpler tech-bin script and a simple
generic ERP recipe." Three small things, each obvious on its own.

Decided against:

- ERP reading the zip itself. The archive's contents are unpredictable
  (Kris), and the rules for that belong in one tool with a name, not
  in a reader inside a pipeline that should stay simple.
- Salvaging a truncated csv. The SBS replica salvages because a
  download is what it is; an archive from IT should be complete, so a
  broken one is refused and reported, and nothing half-written is
  left. If that ever bites, it is a deliberate feature to add.
- Sniffing encoding or delimiter. Defaults with overrides. Sniffing is
  where quiet corruption comes from.
- Naming outputs after the archive (`<zip>__<member>`). Kris: same
  name as the csv. Collisions are refused, not renamed.

Numbers the design rests on (from the replica's manifest, 2026-09-13):
15.5 GB of IMS csv became 373 MB of Parquet at zstd level 1 (41.6:1);
level 15 takes another ~13% at no read cost. A 600 MB csv is ~1.9 M
rows at ~320 bytes/row - past Excel's limit - so the Parquet is the
durable artefact and an xlsx is a convenience when the count allows.
That decision lives in the wrapping script, not here.

Streaming: pyarrow.csv.open_csv reads the zip member as a file-like
object in 8 MB blocks; a ParquetWriter emits a row group every
~262K rows. Memory is bounded by the block and the pending row group,
whatever the csv's size. The header is read once first (a cheap open
that reads only the first block) so every column can be declared text.
