# Design, and what was decided against

`dev_notes/2026-09-13_design.md`

The tool converts; it does not decide anything about xlsx, row limits
or recipes. Kris's cut (2026-09-13): "the tool that creates Parquet
from any csv files in the zip should just do that. Normally only one
file will come out, and it will be pretty small. That can then be
converted individually by a much simpler tech-bin script and a simple
generic ERP recipe." Three small things, each obvious on its own.

Decided against:

- ERP reading the zip itself. The archive's contents are unpredictable
  (Kris), and the rules for that belong in one tool with a name, not
  in a reader inside a pipeline that should stay simple.
- Salvaging a truncated csv. The SBS replica salvages because a
  download is what it is; an archive from IT should be complete, so a
  broken one is refused and reported, and nothing half-written is
  left. If that ever bites, it is a deliberate feature to add.

  BUT (2026-09-14, first real file): "refuse anything that does not
  parse" was too broad. The 600 MB IMS csv failed at once - "Expected
  39 columns, got 14" on a line beginning with a workflow value, i.e.
  the tail of a record split at a line break inside a note. Cause: an
  inner quote the export never doubles (`40" high`), which a strict
  parser reads as closing the field. That is a property of every
  complete IMS file, not of a broken one, so it is repaired, not
  refused: inner_quotes.py is the replica's escape_inner_quotes rule
  as a streaming file-like wrapper with one byte of lookahead held
  across chunks, proven byte-identical to the replica's whole-buffer
  version on nine shapes at six chunk sizes. Truncation is still
  refused. The distinction: repair what the EXPORTER always gets wrong;
  refuse what a download sometimes gets wrong.
- Sniffing encoding or delimiter. Defaults with overrides. Sniffing is
  where quiet corruption comes from.
- Naming outputs after the archive (`<zip>__<member>`). Kris: same
  name as the csv. Collisions are refused, not renamed.

Numbers the design rests on (from the replica's manifest, 2026-09-13):
15.5 GB of IMS csv became 373 MB of Parquet at zstd level 1 (41.6:1);
level 15 takes another ~13% at no read cost. A 600 MB csv is ~1.9 M
rows at ~320 bytes/row - past Excel's limit - so the Parquet is the
durable artefact and an xlsx is a convenience when the count allows.
That decision lives in the wrapping script, not here.

Streaming: pyarrow.csv.open_csv reads the zip member as a file-like
object in 8 MB blocks; a ParquetWriter emits a row group every
~262K rows. Memory is bounded by the block and the pending row group,
whatever the csv's size. The header is read once first (a cheap open
that reads only the first block) so every column can be declared text.


## The second real-file lesson (2026-09-14): `""` is ambiguous

The port above was not enough: the same file failed the same way. The
bytes (Kris printed the lines around the break) showed a COMPLETE row
cut at `"Block Pink Salmon Green Roe P-1F 3 x 7.5"` - a value ending in
an inch mark, written as `7.5""` before the delimiter. Standard csv
reads `""` as an escaped quote and keeps the field open; the parser
swallows `,SALMON,PINK,...`, the line break, and part of the next row.
The replica's reader has the same blind spot, and its manifest shows a
BLANK parse note for this file with 1,728,632 rows - so it may have
merged such rows silently; a query on the replica's Parquet for a
Product Name containing `",SALMON,` would show whether it did.

No local reading of the bytes can decide `""`. What decides it is a
property of the exporter: one that never doubles quotes cannot have
written an escape. `--undoubled-quotes` says so, and under it every
quote inside a field not followed by delimiter / line end / EOF is an
inner quote, including one followed by another quote. Off by default,
so an exporter that escapes properly is read as standard. A dialect
flag, not knowledge of any system; the launcher for a given exporter
sets it.


## The third real-file lesson (2026-09-14): it was a truncated download

With the diagnosis in place the bytes said it plainly: record
1,728,632 is the LAST line, 14 of 39 fields, no final newline. The
600 MB pull - the longest of them all - had stopped mid-record. Not the
inner-quote case, not the `""` case; the shape the tool refuses on
purpose. The replica had salvaged it (its manifest says 1,728,632 rows,
the complete ones) and Kris's zero-count query confirmed nothing was
merged. Kris: shouldn't that be detectable algorithmically - literally the
last line, incomplete? Yes, and unambiguously: nothing but a stopped
download produces a short LAST record with no final newline. So the
drop is automatic and reported; `--strict` refuses instead. A short
record anywhere else, or a short last record that ends with a newline,
is a bad row and is refused. Requiring a flag for something the
evidence already proves was policy dressed as caution.

What to take from three rounds on one file: the first two fixes were
built on inference from a partial diagnostic (the first line starting
with a workflow value, which is just the first row IN that workflow).
The diagnosis that prints the failing record's bytes should have been
the FIRST thing built, not the third. It is now part of every refusal.
